GO HEALTH｜健康生活服務

將尚未收斂的健康新事業命題，收斂為服務定位、MVP 範圍、功能架構與使用流程，推進需求規格、測試驗收與公開上線；上線後建立產品觀測方式，提出 P1.1 優化與後續 Roadmap 議題。

1. Context｜專案背景

GO HEALTH 是 HAPPY GO 健康生活服務的第一階段 Web MVP。專案初期從認知保健、健康內容與會員日常互動切入，嘗試將 HAPPY GO 既有點數與會員關係，從消費回饋延伸至健康生活、家庭／朋友互動與長期會員經營場景。

這不是一個一開始就有完整需求文件的產品，而是一個需要在產品定位、使用者情境、內容入口、任務機制與活動導流之間逐步收斂的會員服務題目。

2. Challenge｜挑戰

第一階段真正要解的問題，不只是功能如何做，而是要確認 HAPPY GO 會員是否願意在消費回饋之外，開始參與健康生活服務。

上線後，產品需要回答的不只是「會員是否願意進入健康生活服務」，也包含健康點是否有足夠明確的使用價值、首週互動後如何形成持續回訪，以及產品定位與長期價值如何持續收斂。這些問題需要透過入口、任務、互動天數、群組使用、發券與回訪等指標持續觀察。

會員是否願意接受健康生活服務？

健康議題與點數會員服務之間，需要一個足夠自然、低壓的入口。

健康內容與任務能否降低參與門檻？

內容、任務、點數與遊戲化回饋，需要轉化為會員願意開始的日常互動。

MVP 能否支持下一階段判斷？

第一版產品需要留下足夠的行為觀察，支持後續 P1.1 優化與 Roadmap 判斷。

3. My Role｜我的角色

  • 主責第一階段 MVP 範圍、功能架構、使用流程與需求規格收斂，並協調跨部門完成測試驗收及公開上線。
  • 規劃健康內容入口、每日任務、健康點累積、群組互動與活動導流機制。
  • 與醫療合作單位協作，將專業衛教內容轉化為一般會員可理解、可進入互動流程的內容入口。
  • 撰寫 User Flow、Wireframe、功能規格與測試文件，補齊空狀態、錯誤引導與跨頁銜接等邊界情境。
  • 協調工程、營運、會員、數據、品牌、公關及亞東醫院等內外部單位，推進開發、測試驗收與公開上線。
  • 在設計與前端資源有限的情境下，運用 AI 工具完成前端雛形與互動原型。
  • 建立輕量內容管理方式，降低驗證與日常內容調整對工程排程的依賴。

4. Product Decisions｜關鍵產品判斷

在 Web MVP 條件下收斂可驗證範圍

在 Web MVP 的既定條件下，優先建立內容入口、任務、健康點與群組等可觀測流程，讓第一階段產品能支持後續判斷與版本規劃。

從認知保健切入

不一次展開所有健康議題，而是從認知保健與日常互動開始，降低理解成本與溝通風險。

用任務與健康點降低參與門檻

以每日任務、健康點與互動遊戲，讓健康議題從文章閱讀轉成可開始、可完成、可累積的行為。

規劃「參與—累點—兌換」循環

提出健康點兌換 HAPPY GO 點數的規則與成本試算，讓健康互動能連回 HAPPY GO 生態圈，強化會員參與誘因。

用群組機制測試陪伴行為

透過家庭／朋友群組觀察陪伴、提醒與週期回饋，是否有機會提高參與與回訪。

用輕量內容管理降低工程依賴

在上線前後內容頻繁調整的情境下，讓營運團隊能維護文字、區塊與顯示狀態，降低對工程排程的依賴。

5. Validation Map｜驗證方向

第一階段 GO HEALTH 的重點，不是一次完成完整健康平台，而是透過健康內容、任務、健康點與群組互動，觀察 HAPPY GO 會員是否願意在消費回饋之外，開始參與健康生活服務。

上線後，我將觀測重點整理為三個層次：入口是否能被理解、任務是否能被完成、互動是否有機會被延續。

入口理解

觀察會員是否能理解 GO HEALTH 提供什麼、為什麼要進入，以及健康任務與點數回饋之間的關係。

任務參與

觀察會員是否願意開始任務、完成互動、累積健康點，並透過活動或內容入口進一步探索服務。

關係延續

觀察群組、回饋與週期性內容是否有機會讓健康互動從一次性參與，延伸為家庭／朋友之間的陪伴與提醒。

初步觀察顯示，有效群組成員有較高的多日互動比例，但目前只能視為「群組可能有助於回訪」的假設，仍需透過更多樣本與後續觀察驗證，也不能排除高參與使用者較容易加入群組的自我選擇。

6. Current Status / Value｜目前成果與價值

  • 完成第一階段核心流程、需求規格與測試驗收，於 2026 年 7 月公開上線。
  • 建立健康內容、每日任務、健康點、群組互動與活動導流的基礎服務流程。
  • 協助 HAPPY GO 建立從點數與消費回饋場景延伸至健康生活服務的第一版產品架構。
  • 建立輕量內容管理流程，提升活動期間內容調整與後續營運彈性。
  • 主動建立會員開通、任務參與、互動天數、群組使用與回訪留存等觀測指標，並依上線初期數據及使用回饋提出 P1.1 優化；現階段將會員開通流程、回訪路徑、兌換誘因與群組機制列為後續優先驗證方向。

7. Reflection｜專案反思

這個專案讓我重新理解 0→1。MVP 的價值不只在於把第一版功能做出來，而是建立一個能被觀察、能被調整，也能支持下一階段判斷的產品基礎。

對 GO HEALTH 來說，第一版產品必須同時處理健康內容、會員入口、任務誘因與群組互動；上線後則需要透過參與數據與營運回饋，持續判斷哪些機制值得加深、哪些入口需要調整，以及下一階段 Roadmap 應該如何收斂。

這也是我在這個專案中的主要學習：Product Manager 不只是推進功能上線，而是要讓產品在上線後有被觀察與被迭代的結構。
